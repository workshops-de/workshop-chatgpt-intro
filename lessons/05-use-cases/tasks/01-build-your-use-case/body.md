## Overview

This is where the day comes together. You will take one recurring task from your own work, run it through properly, judge the result honestly, and turn it into something you can reuse next week without rebuilding it from scratch.

## Prerequisites

- A configured account and a project from Lesson 2
- A working prompt from Lesson 3
- One recurring task and real material for it

If nothing of your own works here, build the assistant around the meeting notes from the Lesson 3 materials. Turning rough notes into a clean summary with decisions and owners is a genuinely recurring task, and you can judge the result immediately — which is the third selection question answered.

## Steps

### 1. Apply the three questions

Take your best candidate and check it:

- Is it mostly text?
- Does it come back at least monthly?
- Can you tell a good result from a bad one within a minute?

If any answer is no, switch to a different task now rather than discovering the problem at the end.

### 2. Run it for real

Do the task with real material, start to finish, exactly as you would on a normal working day. No demo example.

Iterate until the result is genuinely usable, and keep track of how many follow-ups it took.

### 3. Judge it honestly

Answer three questions in writing:

- How long did this take compared to doing it yourself?
- What did you have to fix, and would you have caught it if you were rushing?
- Would you put your name on this result?

If the honest answer to the last one is no, that is a finding, not a failure. Write down what is missing.

### 4. Make it reusable

Choose the level that fits how often the task recurs:

| Frequency | What to build |
|---|---|
| Monthly | Save the prompt in a note |
| Weekly | Project with instructions and reference files |
| Weekly, several colleagues | A custom GPT you can share |

Build it now, while you still remember what mattered.

### 5. Test it cold

Open your saved project or GPT and run a second, different real example through it — without adding any explanation you did not put into the instructions.

Whatever it now gets wrong is missing from the instructions. Add it and test once more.

### 6. Note the boundary

Write one sentence describing where this use case stops: what you will always check by hand, and what you will never put in.

## Success Criteria

- [ ] A task chosen that passes all three questions
- [ ] The task completed with real material to a usable result
- [ ] An honest assessment written down, including the time comparison
- [ ] A reusable version built at the right level
- [ ] A cold test run, with the instructions improved afterwards
- [ ] The boundary of the use case stated in one sentence

## Troubleshooting

**"It took longer than doing it myself."**
Common and worth reporting to the group. Usually one of three things: the task was too small to be worth the setup, the material was not supplied, or the task actually belongs in the judging column. Work out which, because that diagnosis is more valuable than a working prompt.

**"The cold test was much worse than the first run."**
Exactly what this step is for. During the first run you kept adding context in conversation and did not notice. All of that has to move into the instructions.

**"My task needs internal knowledge it cannot have."**
Attach it as a reference file in the project, if your plan and policy allow. If they do not, that is a real organisational finding and belongs in your notes for Lesson 6.

Do not sit the exercise out in that case. Build the same thing on a private recurring task instead: the weekly meal plan, the training schedule, the reading list, the packing list you rewrite before every trip. The moves are identical — instructions, reference files, cold test — and you take the skill back to work even though the material stayed at home.

**"I cannot decide between a project and a GPT."**
Start with the project. A GPT only pays off when someone else uses it, and you can promote it later.
